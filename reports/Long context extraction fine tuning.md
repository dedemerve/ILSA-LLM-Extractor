# Fix the pipeline before judging fine-tuning

The failed Mistral-7B LoRA run does not show that fine-tuning cannot work at this data size. It shows that the run was never a valid test. The repository and Colab notebooks record a training setup that could not have learned to stop: `pad_token = eos_token`, loss over the whole sequence (the gold JSON is only **6.5% of training characters**), and a `max_seq_length=32768` checked only with a chars/4 estimate against inputs of about 101k characters, which can push the closing `]` and EOS past the truncation point. The evaluation adds its own confounds. BASE and LoRA were scored on **different splits**. The same LoRA predictions score **F1 = 0.00 or 0.381** depending on which matcher is used. The adapter may never have been loaded, because `load_state_dict(strict=False)` silently skips mismatched keys. And "val loss 1.42→1.50" mostly measures how well the model predicts the source papers, not the extraction. On the technical questions, the answers are these. 32k QLoRA on an A100-40GB is feasible with 4-bit NF4, offloaded gradient checkpointing, FlashAttention-2 and a fused cross-entropy, ideally through Unsloth, though memory was not what broke this run. LoRA rank barely matters at N≈30 studies, while step count, completion-only loss and checkpoint selection do. Constrained decoding plus chunked extraction is the most reliable defence against loops. Qwen3-8B (non-thinking) or Llama-3.1-8B is a better base than Mistral-7B v0.3. Pair F1 matched on construct alone is not a defensible primary metric. The honest strategic verdict: at 29–30 training documents, fine-tuning is worth keeping only as a cleanly run, pre-registered comparison arm against RAG-plus-few-shot prompting. The downstream claim that better extraction lowers PISA forecasting MAE is very likely to come out null under the current Ridge design and should be reframed now.

## 32k QLoRA fits on 40 GB once four tensors are tamed

At 16k–32k tokens the frozen weights stop being the main memory cost. Four tensors matter, and each technique targets a different one. **4-bit NF4 QLoRA** shrinks the weights from about 14.5 GB to about 4–4.5 GB. **Gradient checkpointing**, preferably with CPU offload, removes the per-layer activations. Saving only the layer boundaries costs roughly 32,768 × 4,096 × 2 bytes × 32 layers ≈ 8.6 GB, which offloading moves almost entirely to host RAM. **FlashAttention-2** makes attention memory linear in sequence length. A **fused or chunked cross-entropy** removes the logits tensor. For Mistral's 32,768-token vocabulary that tensor is about 1.07 billion elements, roughly 4.3 GB per fp32 copy and 8–17 GB on the unfused path. These figures are back-of-envelope arithmetic from the [Mistral-7B-Instruct-v0.3 config](https://huggingface.co/mistralai/Mistral-7B-Instruct-v0.3/raw/main/config.json) and still need a measured dry run.

Combined, the estimates are about 25–35 GB at 32k without a fused cross-entropy (it fits, but tightly), about 18–22 GB with one, and about 10–14 GB with offloaded checkpointing as well. Published measurements back the ordering. Unsloth's table for Llama-3.1-8B QLoRA (r=32, all linear layers, batch 1) gives a **maximum context of 153,977 tokens on 40 GB, against 12,264 for plain HF + FA2** ([Unsloth benchmarks](https://unsloth.ai/docs/basics/unsloth-benchmarks)). Unsloth attributes this to offloaded gradient checkpointing combined with Apple's Cut Cross-Entropy. CCE cuts the classifier head's training memory on Gemma 2 from 28 GB to 1 GB and runs forward plus backward on an A100 in 134.8 ms with 1,164 MB, against 208.8 ms with 28,000 MB for the baseline ([arXiv 2411.09009](https://arxiv.org/abs/2411.09009)). For Mistral 7B on a 24 GB L4, Unsloth reported about 5K tokens for native HF, about 14K with FA2 and about 56K with its offloading ([Unsloth long-context blog](https://unsloth.ai/blog/long-context)). Those are vendor numbers, but the direction is clear.

Packing and padding-free collation do not help this workload, and the brief's question rests on that misconception. Packing improves throughput, by up to 2× on FLAN for Mistral-7B with 20% lower peak memory ([HF blog: Packing with FA2](https://huggingface.co/blog/packing-with-FA2)), but it cannot lower the peak for a single 32k example at batch size 1. TRL's default `"bfd"` strategy also **discards overflow tokens**. `"bfd_split"` keeps them but breaks the link between prompt and JSON, and `"wrapped"` is documented as hurting performance ([TRL reducing memory](https://huggingface.co/docs/trl/v1.9.2/reducing_memory_usage)). Use `packing=False`. **Completion-only loss** belongs in the memory discussion too. In chunked loss paths that drop −100 positions before the lm_head, logits are computed only for the JSON tokens, so the logits problem nearly disappears. More importantly, it fixes the 6.5%-target-share defect. One compatibility trap: TRL v1.9.2 documents `loss_type="chunked_nll"` as incompatible with PEFT and with Liger, while the v1.15.0 docs call it a deprecated alias of `nll` ([TRL v1.9.2](https://huggingface.co/docs/trl/v1.9.2/reducing_memory_usage); [TRL v1.15.0](https://huggingface.co/docs/trl/sft_trainer)). Use exactly one loss replacement: Unsloth's built-in CCE, or Liger FLCE, or `cce_patch`. Never stack them.

Mistral-7B v0.3 itself has `max_position_embeddings=32768`, `rope_theta=1e6` and `sliding_window=null`. The 4,096-token sliding window belonged to v0.1, so v0.3 has no window caveat, but the prompt plus the JSON must fit inside 32,768 tokens ([config.json](https://huggingface.co/mistralai/Mistral-7B-Instruct-v0.3/raw/main/config.json)). Since the real training inputs probably exceed that, the right fix is section selection or chunking. RoPE scaling and silent truncation are both the wrong answer. If 40 GB proves fragile, an 80 GB A100 rents for about $1.19–1.49/h on RunPod and $1.49/h on Jarvislabs ([Jarvislabs](https://jarvislabs.ai/blog/a100-price); [RunPod review](https://www.hackceleration.com/labs/runpod-pricing)), and the whole training run costs under about $20.

The recommended stack pins **trl 1.15.0, transformers 5.19.0, peft 0.21.2** ([PyPI](https://pypi.org/)), plus a recent Unsloth release, flash-attn 2.x built for the installed torch, torch ≥ 2.4 and Triton ≥ 3.0 for CCE. The original run used transformers 4.47.0, peft 0.14.0 and trl 0.13.0, which predate the current `completion_only_loss` and `max_length` semantics. Record `pip freeze` in the run manifest. The configuration below is untested; check the Unsloth API names against its current documentation.

## At 29 documents, the step count and the baseline matter more than the rank

Rank is not the lever. Thinking Machines' "LoRA Without Regret" found that on small-to-medium SFT datasets, LoRA matches full fine-tuning's learning curves "with the same sample efficiency". With the standard α=32 parametrization, the optimal learning rate is nearly independent of rank and shifts by less than 2× between r=4 and r=512, at about **10× the full-fine-tuning LR**. **Attention-only LoRA underperforms MLP-only LoRA** ([Thinking Machines](https://thinkingmachines.ai/blog/lora/)). The original run used attention only (q/k/v/o), so moving to `target_modules="all-linear"` ([HF PEFT](https://huggingface.co/docs/peft/package_reference/lora)) is the best-supported single change. Going from r=16 to r=4 or r=8 will not fix overfitting on its own. What will fix it is cutting the number of optimizer steps (about 12.6 epochs over 29 examples is far too many), selecting the checkpoint by validation extraction F1, and making the loss count only the target tokens. A reasonable grid is r ∈ {8, 16} with α fixed at 16–32, LR ∈ {1e-4, 2e-4}, and 1–3 epochs. None of the cited LoRA studies trains on fewer than a few thousand examples, so these settings are extrapolations.

**RSLoRA and DoRA are not regularizers and are low-ROI here.** `use_rslora=True` changes the scale from α/r to α/√r. At r=16 and α=32 that turns a scale of 2 into a scale of 8, effectively a 4× higher LR, which would worsen overfitting unless the LR is retuned ([PEFT docs](https://huggingface.co/docs/peft/package_reference/lora); [arXiv 2312.03732](https://arxiv.org/abs/2312.03732)). DoRA "can improve the performance of LoRA especially at low ranks" but has more training overhead and does not work with multi-adapter batching ([PEFT](https://huggingface.co/docs/peft/package_reference/lora); [arXiv 2402.09353](https://arxiv.org/abs/2402.09353)). It also complicates adapter serving. No evidence was found that either helps at N < 1,000, so treat them as optional ablations at most. NEFTune's gains come from judge-scored chat quality (LLaMA-2-7B AlpacaEval rose from 29.79% to 64.69%), not from structured extraction ([arXiv 2310.05914](https://arxiv.org/abs/2310.05914)).

The larger question is whether to fine-tune at all. Published fine-tuning wins share three features: short inputs, mostly verbatim spans, and 100–600+ examples. Dagdelen et al. found that output structure appeared only around 20 training samples, using sentences and abstracts as inputs ([Nature Comms 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC10869356/)). LoRA Land's average gains over GPT-4 were smallest on broad, complex tasks ([arXiv 2405.00732](https://arxiv.org/abs/2405.00732v1)). This task fails all three conditions. The inputs are full papers. `canonical_construct` requires mapping to a codebook. `plausible_values_handling` and `student_weights_used` live in methods sections far from the results. Prompt-only frontier models reach 76–91% on metascience variable extraction but drop on variables that need inference ([JYX](https://jyx.jyu.fi/jyx/Record/jyx_123456789_111061)). Social-science studies were GPT-4's hardest domain, at 72% against 80–82% elsewhere ([arXiv 2405.14445](https://arxiv.org/pdf/2405.14445)). ChatExtract shows that a prompt-only find-extract-verify pipeline can reach about 90% precision and recall with no training data ([arXiv 2303.05352](https://arxiv.org/abs/2303.05352)). Nobody has measured a crossover point for long-document, inference-heavy extraction, so "fine-tuning will lose at N=30" is a hypothesis to test, not a fact. It is, however, the expected outcome.

Cost does not decide the question. Zero-shot extraction of an ~18k-token paper costs about $0.01 (Gemini 2.5 Flash), $0.02 (Llama 3.3 70B on Together at $1.04/M), or $0.04 (GPT-5 at $1.25/$10). Few-shot with two full-paper demonstrations stays under about $0.20 per paper ([Together pricing](https://www.together.ai/pricing); [requesty](https://requesty.ai/models/compare/openai--gpt-5/google--gemini-2-5-flash)). These figures come from aggregators and need re-checking. A Llama-3.1-8B fine-tune on Together hits the **$4 job minimum** ([Together pricing](https://www.together.ai/pricing)). The real cost of fine-tuning is researcher time and evaluation complexity. **RAG-augmented few-shot prompting has the best ROI.** Retrieve methods sections for the PV and weights fields and results sections and tables for the effects, add one to three gold-annotated demonstrations chosen by embedding similarity from the training studies only, and add a ChatExtract-style verification pass. This uses the gold set without training on it and can be evaluated on exactly the same study folds.

A defensible thesis design runs four or five arms on identical study-level folds. They are: (1) zero-shot with a JSON schema on a frontier API, (2) RAG few-shot on a frontier model and on Llama-3.3-70B or a Qwen3 model via Together, (3) the base 7–8B model with the same prompt, (4) the LoRA 7–8B model trained on chunk-level examples, and optionally (5) a verify pass on the best arm. Arm 3 versus arm 4 answers the clean scientific question, whether LoRA helps a small model, and will probably show gains in format and canonical labels. Arm 4 versus arm 2 answers the practical question, and will probably show that it is not worth it at this N. Both are publishable. Teacher distillation (pre-annotating new papers with the best prompting arm, then human verification) is the best way to grow the gold set beyond 42 studies. In Dagdelen's study, model pre-annotation cut human annotation time per abstract by 57% ([PMC10869356](https://pmc.ncbi.nlm.nih.gov/articles/PMC10869356/)).

## Layered JSON defences stop loops that no single fix stops

No single technique prevents both truncation and repetition, so the defence needs layers.

**Training (the root cause).** Use a distinct pad token (`unk` for Mistral) and completion-only loss. Never truncate a target. Serialize gold arrays deterministically, with fixed key order, compact separators and items ordered by their position in the text, so the model has a monotone pointer through the paper. Include `[]` (or `{"items": []}`) examples for chunks with no evidence, so the model has a learned short exit.

**Serving.** Grammar-constrained decoding through **vLLM 0.31.0** with the **llguidance 1.9.1** (`guidance`) or **xgrammar 0.2.8** backend guarantees schema-valid JSON. After the closing `]` the only legal continuation is EOS, which forces termination even in a model that never learned to stop ([vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs.html)). Constrained decoding does not hurt quality. JSONSchemaBench measured GSM8K accuracy on Llama-3.1-8B at 80.1% unconstrained against 83.7% (XGrammar) and 83.8% (Guidance) ([arXiv 2501.10868](https://arxiv.org/html/2501.10868v2)). That result contradicts the earlier "Let Me Speak Freely?" degradation claim ([arXiv 2408.02442](https://arxiv.org/abs/2408.02442)). Backend coverage varies, though. On hard schemas Outlines reached 0.03 coverage, largely through compile timeouts on `minItems`, `maxItems` and `enum`, and XGrammar had 38 under-constrained test categories against 1 for Guidance ([JSONSchemaBench](https://arxiv.org/html/2501.10868v2)). Prefer llguidance, avoid Outlines (1.3.3) for array schemas, and treat lm-format-enforcer (0.11.3, last released August 2025) as the slow-moving option.

Constrained decoding does not stop **semantic loops**: the model can keep emitting identical, schema-valid objects up to the item cap. Gemini users have documented schema-constrained output looping inside an unbounded number field until it hit max tokens ([Google AI forum](https://discuss.ai.google.dev/t/structured-output-repetition-loop-inside-a-json-number-literal-runs-to-max-tokens-flash-vertex/175138)). So the schema needs `maxItems` (set from the per-chunk p95 gold count), `enum` for `effect_type`, `direction`, `plausible_values_handling`, `student_weights_used` and ideally `canonical_construct`, `maxLength` on `predictor`, `outcome` and `evidence_text`, plus `additionalProperties: false` and all fields required. Do not rely on `uniqueItems`; deduplicate in post-processing. Use a top-level object wrapper, `{"items": [...]}`.

**Decomposition** shortens each output, which is the strongest structural defence for a 7B model. Split the paper into sections or windows of about 1–2k tokens. Extract with `maxItems` of about 8 and `max_tokens` of about 1,200 per chunk. Merge, deduplicate on normalized (predictor, outcome, canonical_construct) keeping the longest `evidence_text`, and drop any item whose `evidence_text` does not fuzzy-match its chunk. Chunking also multiplies the 29 training documents into a few hundred examples and removes the 32k truncation problem. The cost is that document-level fields (PV handling, student weights) need a separate pass over the methods section. A two-stage design (list the pairs first, then fill the slots) is the alternative when recall control matters.

**Decoding and validation.** Use greedy decoding with a small `frequency_penalty` of 0.1–0.3, which in vLLM applies only to generated tokens and so does not penalize verbatim copying from the source. Avoid `no_repeat_ngram_size`, because JSON keys legitimately repeat, and keep any `repetition_penalty` at or below 1.1. TGI's example uses 1.3 with a grammar ([TGI guidance docs](https://huggingface.co/docs/text-generation-inference/basic_tutorials/using_guidance.md)), which is too aggressive when `evidence_text` must copy prompt tokens. Treat `finish_reason=="length"` as a failure. As a last layer, validate with Pydantic. **instructor 1.17.0** (`from_openai` against the vLLM endpoint, `max_retries=1`, `create_iterable` so that items are validated one at a time) adds re-asking but not constrained decoding, so a looping model just multiplies its cost ([instructor docs](https://python.useinstructor.com/)).

Mistral function calling works in vLLM (`--tool-call-parser mistral`), and a named `tool_choice` is enforced through the same structured-output machinery ([vLLM tool calling](https://docs.vllm.ai/en/latest/features/tool_calling.html)). It would, however, require reformatting the SFT data into `[TOOL_CALLS]` syntax for no gain over `response_format` with a JSON schema.

Two deployment facts contradict the brief. **Together has discontinued serverless LoRA inference**, so adapters now run on paid dedicated endpoints ([Together LoRA docs](https://docs.together.ai/docs/lora-inference)). This supersedes the 2024 multi-LoRA announcement. **TGI is in maintenance mode**, with vLLM or SGLang recommended instead ([TGI GitHub](https://github.com/huggingface/text-generation-inference)). HF Inference Providers do not document serving text-generation LoRA adapters. On a minimal budget, the cheapest way to serve the adapter is batch inference with vLLM on the A100 already in hand, or an HF Inference Endpoint running the vLLM engine with `enable_lora=true` only during extraction runs ([HF Endpoints vLLM](https://huggingface.co/docs/inference-endpoints/en/engines/vllm)). Together's serverless tier stays useful for the base-model and 70B prompting arms, which support `response_format` with a JSON schema ([Together structured outputs](https://docs.together.ai/docs/inference/chat/structured-outputs)).

The first choice is **Qwen3-8B in non-thinking mode**. It has the best 32k retrieval at 8B, the inputs fit inside its native 32k window with no YaRN (the model card warns that static YaRN can degrade short-text performance), it is Apache-2.0, and Unsloth and vLLM support are mature ([Qwen3-8B card](https://huggingface.co/Qwen/Qwen3-8B)). Train on direct JSON with `enable_thinking=False`, because thinking mode lowered Qwen3-8B's 32k RULER score from 91.2 to 80.8 ([Qwen3 report](https://arxiv.org/html/2505.09388)). Qwen3 auto-patches TRL's `{% generation %}` markers, so `assistant_only_loss=True` works without template surgery ([TRL docs](https://huggingface.co/docs/trl/sft_trainer)).

The second choice is **Llama-3.1-8B-Instruct**, the low-risk alternative. It is the only small model with both a published 40 GB long-context QLoRA measurement and Together fine-tuning support (131,072-token LoRA context, $0.34 per million tokens), which makes it the fastest no-GPU ablation. **Qwen3-14B** is the upgrade if the 8B results plateau, but a 14B QLoRA run at 32k on 40 GB needs a feasibility test.

Several candidates should be deprioritized. Qwen3.5-9B has a 262k native context and Together support, but Unsloth says "it is not recommended to do QLoRA (4-bit) training on the Qwen3.5 models", bf16 LoRA needs about 22 GB at base context, and it requires vLLM ≥ 0.17 ([Unsloth Qwen3.5](https://unsloth.ai/docs/models/qwen3.5/fine-tune)). Gemma 3 12B IT drops to 80.3 at 32k and relies on a 1,024-token local window. Gemma-2-9B's 8k context rules it out. Ministral-8B carries a non-commercial license. Phi-3.5- and Phi-4-mini, at 3.8B, have the long-context numbers but less extraction capacity and no Together path. RULER is synthetic retrieval, so these rankings are an upper-bound proxy. Run each candidate zero-shot on the validation studies before fine-tuning anything.

## Construct-only pair F1 hides the error that feeds W_j

The current primary metric is the wrong one. `match_pairs()` in `scripts/baseline_inference.py` greedily takes the first unused prediction with the same `canonical_construct`. It ignores outcome and direction, and its result depends on list order. A wrong-direction pair still counts as a true positive, even though direction is exactly what W_j consumes through the consistency term C_j (`scripts/compute_predictor_weights_v2.py`). At the other extreme, the Stage 9 exact composite key conflates detection with slot accuracy and returns 0.00. Document-level extraction benchmarks avoid both failure modes with order-invariant **Hungarian matching** and multiple levels of granularity. ANLS* scores lists by Hungarian assignment and penalizes both missing and hallucinated elements ([arXiv 2402.03848](https://arxiv.org/html/2402.03848v10)). VAREX matches array elements by maximum field overlap ([arXiv 2603.15118](https://arxiv.org/pdf/2603.15118)). SciREX evaluates n-ary relations across whole papers ([ACL 2020](https://aclanthology.org/2020.acl-main.670)).

The metric set to pre-register before anyone touches the test set has six parts. The first is **strict pair F1**: construct is a hard gate, and a pair counts only if construct, normalized outcome class (math, reading, science, other) and direction all agree, with matching by `scipy.optimize.linear_sum_assignment`. The second is **lenient pair F1**, construct only with Hungarian matching and outcome as tie-breaker, kept for continuity with the recorded BASE result. The third is **joint slot F1** per field, where a slot counts only if the pair matched and the slot is correct; this prevents a model that matches fewer pairs from looking better. The fourth is a deterministic **evidence grounding rate**: a fuzzy substring match of `evidence_text` against the source, with partial ratio ≥ 0.9. The fifth is the **schema-validity and loop rate**. The sixth is per-stratum (HIGH, MID, LOW, SINGLE) and per-study macro scores. A composite similarity such as 0.5·outcome + 0.3·direction + 0.2·effect_type is a design choice with no literature validation, so report a sensitivity table across two or three weightings.

Uncertainty should come from a bootstrap over **studies**, not rows. With six test studies, also report the exact sign-flip test, whose smallest two-sided p-value is 2/64 ≈ 0.031 ([Dror et al. 2018](https://aclanthology.org/P18-1128/); [Berg-Kirkpatrick et al. 2012](https://aclanthology.org/D12-1091/)). Re-scoring the existing BASE test predictions with the new matcher is legitimate, because the matcher does not use the model.

Use an LLM judge only for free-text slots (`outcome` equivalence, and whether `evidence_text` entails the extracted direction), never for the controlled-vocabulary fields. Validate it first on 100–150 train and validation pairs with Cohen's κ or Gwet's AC1, and use a judge from a different model family than the extractor. JUDGE-BENCH found large variance across judges and tasks ([ACL 2025](https://aclanthology.org/2025.acl-short.20)), and judges skew lenient even when percent agreement looks high ([arXiv 2406.12624](https://arxiv.org/html/2406.12624)). The only reliability figure in the repository is **intra-rater** κ = 0.871. A second annotator on 8–10 studies would give a like-for-like human pair F1 under the same matcher. Present it as context, not as a ceiling, since models can exceed noisy human agreement ([Richie et al., BioNLP 2022](https://preview.aclanthology.org/setup/2022.bionlp-1.26)).

**Downstream MAE cannot carry the thesis claim alone.** In `run_loco_forecasting.py`, M1 multiplies standardized `lag_` covariates by √w_j inside `RidgeCV`. That is algebraically a generalized ridge penalty α/w_j, so any uniform rescaling of W is absorbed when α is re-selected. W_j is also min-max normalized (ESCS = 1.00, HOMEPOS 0.15, TEACHER_QUALITY 0), covariates without a weight key default to 0.5, the fill-rate filter drops covariates, and score-lag features at weight 1.0 dominate the prediction. On top of that, the extraction codebook (SCHOOL_BELONGING, ICT_HOME_ACCESS and so on) does not yet map to the W_j keys (BELONGING, ICT_ACCESS and so on). Switching weights fully on or off already moves MAE by at most about 0.3 points on a single PISA 2022 fold of about 90 countries. The BASE-versus-FINETUNED perturbation of W will be smaller still. The existing `diebold_mariano()` also applies a lag-1 Newey-West term across countries, which have no time order, so its result depends on row order. Use paired per-country absolute-error differences with a bootstrap CI and a Wilcoxon test instead, and keep the HLN-corrected DM test for the time-ordered TIMSS folds ([forecast::dm.test](https://search.r-project.org/CRAN/refmans/forecast/html/dm.test.html)).

The defensible extrinsic design has four parts. Compute oracle W from gold, then BASE W and FINETUNED W. Report ΔW (L1 distance and Spearman correlation to the oracle) and C_j sign agreement, which are far more sensitive than MAE. Report ΔMAE with a paired bootstrap and a **TOST equivalence test** against a pre-registered margin, such as one PISA point. And run a **noise-injection dose-response curve**: flip a fraction p of directions, drop a fraction q of pairs and swap constructs at rate r, with about 200 replicates per level, to find how much extraction error MAE can absorb. If even 50% direction flips leave MAE unchanged, the null comes from the forecasting architecture, and the claim narrows to "fine-tuning improves extraction; forecasting is robust to extraction error of magnitude X". No published study measures how LLM extraction error propagates into a downstream forecast, so this design is a synthesis, not an established protocol.

## Conclusion

The thesis question is no longer whether a LoRA adapter can learn ILSA evidence extraction from 29 papers. The recorded run never tested that, because the model was trained mostly to predict source papers, could not learn to stop, may never have had its adapter loaded at evaluation time, and was scored with a matcher that swings F1 between 0 and 0.38. Once those defects are fixed, the scientifically interesting comparison is a fine-tuned 8B model with constrained decoding and chunked extraction against RAG-augmented prompting of a much larger model. The evidence points to prompting winning on accuracy, while fine-tuning may still contribute format reliability and an open-weight, reproducible pipeline. That outcome is publishable if it is pre-registered.

The second shift concerns the propagation claim. The current Ridge design is close to blind to literature weights. A null ΔMAE would then be a property of the forecasting model, not evidence about extraction quality. Making ΔW_j against the oracle and the noise-injection sensitivity curve the main extrinsic evidence, with ΔMAE tested for equivalence rather than superiority, turns a likely null into an informative result about how much extraction error the forecast can absorb.

The repository checks recommended in step 1 were run. They change several statements above.

- **Gold and training population.** Gold is v1.4.1: 42 studies and 246 rows, which collapse to 193 distinct pairs because 53 rows duplicate another row of the same study. Training used the 30 train studies only, and only the 29 that have source text. The model was never trained on all 42 studies.
